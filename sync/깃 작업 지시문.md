````markdown
핵심 원칙은 다음과 같다.

1. GitHub repo는 **룰·스킬·워크플로우·스크립트·설정 템플릿**만 보관한다.

## 1. 반드시 먼저 확인할 것

작업 시작 전 아래를 확인하고, 결과를 `docs/reports/initial_access_check.md`에 기록한다.

### 1.1 현재 작업 위치

다음 정보를 확인한다.

```bash
pwd
ls -la
git status
git remote -v
git branch --show-current
````

Windows PowerShell 환경이면 다음도 확인한다.

```powershell
Get-Location
Get-ChildItem -Force
git status
git remote -v
git branch --show-current
```

### 1.2 GitHub repo 접근 여부

확인할 것:

* 현재 폴더가 Git repo인지
* remote origin이 있는지
* push 권한이 있는지
* branch가 `main`인지, 작업 branch인지
* GitHub Actions나 secret 설정이 필요한지

권장 branch:

```text
main
dev/codex-rules-cleanup
dev/anki-gpt55pro-skill
```

작업은 가능하면 `main`에서 직접 하지 말고 새 branch에서 한다.

```bash
git checkout -b dev/codex-rules-cleanup
```

### 1.3 Drive Sync 접근 여부

다음 후보 위치를 모두 확인한다. 단, 존재하지 않는 경로는 실패로 기록만 하고 넘긴다.

Windows 로컬 후보:

```text

H:\내 드라이브\.codex
H:\내 드라이브\.agent
H:\내 드라이브\.agents

H:\내 드라이브\_sync
H:\내 드라이브\sync_root
```

## 2. 접근 실패 시 보고 규칙

다음 중 하나라도 발생하면 작업을 멈추지 말고 계속 진행하되, `docs/reports/access_failures.md`에 기록한다.

기록 형식:

```markdown
# Access Failures

| 시각 | 대상 | 시도 방법 | 결과 | 추정 원인 | 후속 필요 |
|---|---|---|---|---|---|
| YYYY-MM-DD HH:mm | H:\내 드라이브\.codex | ls/Get-ChildItem | 실패 | Codex Web에서는 로컬 Drive 미마운트 | 사용자에게 파일 업로드 또는 Git 반영 요청 |
```

보고 대상:

* 파일 읽기 실패
* 폴더 존재 확인 실패
* 권한 문제
* Google Drive 포인터 파일 `.gdoc`, `.gsheet`, `.gslides`, `.gscript` 직접 읽기 실패
* 빈 폴더로 보이지만 실제 Drive에는 있을 가능성
* 중복 폴더 때문에 어느 쪽이 최신인지 불명확한 경우
* 동일 파일명이 여러 위치에 있는 경우

절대 추측으로 병합하지 않는다.

````
# SKILL: Anki Card Generation for Law Study

## 0. 목적

이 스킬은 법학 학습 자료를 Anki 카드로 변환하기 위한 규칙이다.
Codex Web/Pro 및 GPT-5.5 Pro 환경에서 실행 가능해야 하므로, Claude·Gemini·Antigravity 등 특정 모델 전용 명령에 의존하지 않는다.

## 1. 우선순위

카드 작업 시 다음 순서로 읽는다.

1. 루트 `AGENTS.md`
2. 과목별 `AGENTS.md`
3. `.agent/workflows/card-wiki-pipeline.md`
4. 이 파일
5. `docs/anki/*.md`
6. `docs/legacy/*.md`는 참고만 한다.

충돌 시 최신 Codex 운영 문서와 `AGENTS.md`를 우선한다.

## 2. 입력

허용 입력:

- `sync/wiki/쟁점/*.md`
- 사용자가 직접 제공한 위키/노트 텍스트
- 검증된 카드 소스
- OCR 원문에서 확인한 발췌
- korean-law-mcp 또는 공적 법령·판례 원문 확인 결과

주의:

- `outputs/02_cards_v37/*.md`는 대량 산출물이므로 Git에 기본 포함하지 않는다.
- Web/Pro 환경에서 해당 파일이 없으면 Drive 자료 요청으로 처리한다.
- 원문 또는 근거가 없는 법리 단정은 만들지 않는다.

## 3. 출력

기본 출력은 Markdown 카드 초안이다.

필요 시 TSV 형식을 사용한다.

Basic 카드:

```text
카드유형: Basic
Front:
Back:
태그:
출처:
검증상태:
````

Cloze 카드:

```text
카드유형: Cloze
Text:
Extra:
태그:
출처:
검증상태:
```

## 4. 카드 유형

### 4.1 Rule 카드

요건, 효과, 법리 일반론을 묻는다.

원칙:

* 하나의 카드에는 하나의 인출 목표만 둔다.
* 요건이 여러 개면 cloze 분할을 우선한다.
* 조문번호가 있으면 조문번호를 정확히 표시한다.
* 조문 원문이 없으면 “조문 원문 미확인”으로 표시한다.

### 4.2 Case-law 카드

판례 법리를 묻는다.

원칙:

* 사건번호·선고일이 확인된 경우에만 판례 anchor를 확정한다.
* 사건번호·선고일이 불명확하면 `[불명확]`으로 표시한다.
* 판례 요지를 임의로 압축해 새로운 법리를 만들지 않는다.

### 4.3 Issue 카드

쟁점 구조, 요건사실, 청구·항변 구조를 묻는다.

원칙:

* 사례형은 청구권/항변/재항변 구조를 유지한다.
* 원고·피고 대립 구조가 있으면 표 또는 단계형으로 분리한다.
* 답안 작성용 암기 포인트와 객관식 판별 포인트를 혼합하지 않는다.

### 4.4 MCQ/OX 카드

객관식·OX 판단을 묻는다.

원칙:

* 정오 근거가 있는 경우만 생성한다.
* “기출/빈출” 태그는 소스에 명시된 경우만 붙인다.
* 해설 없는 단순 OX는 검증필요로 둔다.

## 5. 태그 체계

태그는 최소한 다음 축을 유지한다.

```text
과목::
속성::
주제::
출처::
검증::
```

예시:

```text
과목::민법
속성::판례
주제::부당이득
출처::송영곤_쟁점노트
검증::anchor확인
```

금지:

* 출처 없는 `기출`
* 출처 없는 `빈출`
* 근거 없는 난이도 태그
* 모델 추정 태그

## 6. 근거 규칙

모든 법리·조문·판례 단정은 근거를 붙인다.

근거 형식:

```text
근거 발췌: "..."
근거 위치: 문서명 / 페이지 / 절 / chunk_id
```

위치가 없으면 다음처럼 표시한다.

```text
근거 위치: 확인 불가 — 위치 식별자 부족
```

근거가 없으면 카드를 만들지 말고 다음처럼 출력한다.

```text
자료 부족 — 카드 생성 보류
사유:
필요한 추가 자료:
```

## 7. 검증 상태

카드마다 하나의 검증 상태를 붙인다.

```text
검증::완료
검증::anchor확인
검증::원문확인필요
검증::판례확인필요
검증::조문확인필요
검증::보류
```

## 8. 금지

* 교재 원문 없는 법리 창작
* 조문번호 추측
* 판례 사건번호 추측
* 선고일 추측
* 원문에 없는 예외 창작
* Claude/Opus/Gemini/Antigravity 전용 실행 명령을 필수 경로로 작성
* 대량 outputs를 자동 커밋
* `.apkg`를 Git에 커밋
* 개인 학습 상태를 Git에 커밋
* API key 또는 mcp 설정 실파일 커밋

## 9. apkg 빌드

apkg 빌드는 사용자가 명시 요청하거나 카드 파일을 변경한 경우에만 한다.

빌드 전 확인:

```text
- 변경된 카드 파일 목록
- 총 카드 수 예상
- Basic/Cloze 수
- 한자 잔존 여부
- 번호 없는 cloze 여부
- 과목별 분리 여부
```

빌드 후 확인:

```text
- 총 카드 수
- Basic/Cloze 수
- 과목별 apkg 존재 여부
- 한자 잔존 0
- 번호 없는 cloze 0
```

## 12. 중복 폴더 처리 규칙

다음 폴더가 동시에 있으면 병합 전에 인벤토리를 만든다.

```text
sync
_sync
sync_root
sync이관_2026-06-11
sync_파생본
.codex
.agent
.agents
```

처리 순서:

1. 각 폴더의 파일 목록 생성
2. `AGENTS.md`, `SKILL.md`, `card-wiki-pipeline.md`, `05_anki*`, `이식용_핸드오프*` 우선 탐색
3. 동일 파일명 중복 시 내용 hash 비교
4. modified time 비교
5. 내부 갱신일·운영 메모 비교
6. 불명확하면 사용자 확인 요청

파일 hash 확인 예시:

```bash
find . -type f -name "SKILL.md" -print0 | xargs -0 sha256sum
find . -type f -name "AGENTS.md" -print0 | xargs -0 sha256sum
```

PowerShell:

```powershell
Get-ChildItem -Recurse -Filter SKILL.md | Get-FileHash -Algorithm SHA256
Get-ChildItem -Recurse -Filter AGENTS.md | Get-FileHash -Algorithm SHA256
```

## 17. 최우선 판단 기준

작업 중 애매하면 다음 기준을 따른다.

1. 비밀·대용량·저작권 위험 자료는 Git에 올리지 않는다.
2. Codex Web/Pro가 읽어야 하는 규칙은 Git에 텍스트로 둔다.
3. Drive 자료를 못 읽으면 실패를 기록하고 사용자에게 알린다.
4. 로컬 `H:\내 드라이브` 경로가 없다고 해서 파일이 없다고 단정하지 않는다.
5. 동일 파일이 여러 위치에 있으면 최신성·내용·운영 메모를 비교하고, 불명확하면 병합하지 않는다.
6. 안키 카드화는 `card-wiki-pipeline.md`와 `anki-card-generation/SKILL.md`를 주경로로 삼고, Claude/Gemini/Antigravity 전용 문서는 legacy/reference로 둔다.
7. Web/Pro 실행을 위해 repo는 얇고 재현 가능해야 한다.

```

붙여넣기용으로 더 짧게 쓰려면, 위 문서에서 **0~5번, 10번, 14~17번**만 먼저 넣으면 됩니다. 지금 단계에서는 특히 `Drive Sync Policy`, `Git Policy`, `Codex Web/Pro Runbook`, `anki-card-generation/SKILL.md`를 만드는 것이 우선입니다.
```

1. Codex Web/Pro는 로컬 `H:\내 드라이브` 경로를 직접 읽을 수 없을 수 있으므로, Git repo 안에 필요한 운영 규칙을 최대한 텍스트화한다.
2. 실제 원문·대용량 자료가 필요하면 Drive 경로와 파일명을 명시하고, 접근 실패 시 즉시 사용자에게 보고한다.
3. 파일을 읽지 못했거나 폴더가 비어 보이거나 권한 문제로 접근되지 않으면 추측하지 말고 “읽기 실패/접근 불가/미동기화 가능성”으로 보고한다.

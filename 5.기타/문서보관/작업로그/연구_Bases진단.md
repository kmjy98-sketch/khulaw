## 1. 현 `.base`의 문제 (구체)

### (a) 목차 계층(과목>대분류>논점)이 평면으로 붕괴 — 핵심 결함
- 진도표 뷰는 `groupBy: note.과목` **한 단계만** 그룹화한다(진도보드.base L35~37). 그 결과 민법 132논점이 "민법" 한 덩어리 아래 **평면 나열**된다. MOC가 가진 `민법총칙[01~29] / 채권법[30~84] / 물권담보물권[85~122] / 가족법[G01~G10]` 대분류 계층(`_민법_목차.md`)이 보드에서 사라진다.
- 근본 원인: **frontmatter에 계층 속성이 없다**(중분류/대분류/편/장/절 보유=0, 민법 132 전수). `논점: 86`은 번호일 뿐 분류가 아니므로(법정지상권.md L4), Bases가 그룹화·정렬할 분류 키 자체가 존재하지 않는다. → 보드를 아무리 잘 짜도 데이터에 계층이 없어 평면화는 불가피.

### (b) 중분류 그룹 없음 = 정렬도 무의미
- 진도표 뷰 정렬은 `order: 논점 > 진도 > 회독 > 약점`(L30~34). `논점`이 번호라 정렬하면 **번호순(1,2,…,132)**으로 늘어선다. 교재 단원 흐름(목차 순서)과는 일치하나, 중간 분류 헤더가 없어 132줄을 스크롤하며 "지금 어느 단원인지"를 잃는다(목차 계층 상실의 사용성 증상).

### (c) '쟁점 누락'으로 보이는 현상 = 필터·키 불일치
- 필터 `note.type == "쟁점"`(L1~3). 논점노트 type은 `쟁점`(법정지상권.md L2)이라 매칭은 된다(695 모두). 다만:
  - 보드 단위(논점 695)와 서버보드 단위(BOARD 단원 202)가 **다른 체계**다. MOC 논점명(법정지상권·대상청구권)과 BOARD 단원명(교재 중분류 단위)이 1:1이 아니다 → 서버보드에 익숙한 사용자가 Bases를 보면 "있던 단원이 없다/쪼개졌다"로 느낀다(누락처럼 보이는 정체).
  - 회독진행 뷰(`note.회독 > 0`)·미착수 뷰(`note.진도 == "미착수"`)는 **현재 전 노트가 회독0·미착수**라(진도값 132/132 미착수, 회독 시드 생략 — `bases_진행.md` L11) 미착수=전체, 회독진행=공집합으로 뜬다. 데이터가 0이라 뷰가 비거나 전량이라 변별력 0.

### (d) bool/number 필터 미검증
- 약점 뷰(`note.약점 == true`)·회독진행 뷰(`note.회독 > 0`)의 bool·숫자 비교 문법이 옛 예시(`_쟁점보드.base`는 전부 text 비교)에 없어 **렌더 미검증 상태**로 명시돼 있다(`bases_진행.md` L18). 즉 4뷰 중 2뷰는 동작 보증이 안 된 채 납품됨.

### (e) 중첩 그룹 부재 (구조적)
- 현 .base·옛 .base 모두 `groupBy`에 **단일 property**만 준다(진도보드.base L35; _원문논점보드.base L20·29; _쟁점보드.base L26). 과목>대분류>논점의 2단·3단 중첩 그룹 시도가 없다.

## 2. Bases가 목차 계층 그룹/정렬/중첩그룹을 지원하는가

### 확인된 사실(워크스페이스 소스)
- **단일 groupBy는 확실히 지원**: `groupBy: { property: note.과목, direction: ASC }` 형태가 실제 .base 3종에서 사용됨(진도보드.base L35~37 등). multi-key `order`(정렬 우선순위 리스트)도 지원(L30~34).
- **필터는 text 등치(`==`)가 검증됨**; bool(`== true`)·숫자(`> 0`) 비교는 **미검증**(`bases_진행.md` L18).
- **스코프 주의**: `.base`는 위치 무관 **볼트 전체**가 기본 스코프 → 폴더 한정하려면 `file.inFolder("...")` 필터 명시 필요(PKM구조도 L21, 1차출처 인용).
- **공식 문법 문서 존재**: `obsidian.md/help/bases/syntax`가 PKM 문서에 1차출처로 인용됨(PKM구조도 L142). 단 본문은 워크스페이스에 캡처돼 있지 않음.

### 미확인 (외부 지식 필요 — 추측 금지)
- **다단계 중첩 groupBy(과목>대분류>논점)를 Bases가 네이티브로 지원하는지 = 미확인.** 워크스페이스 소스에는 단일 groupBy 예시만 있고, 중첩 그룹 문법(또는 그 부재)을 직접 보여주는 자료가 없다. 옛 .base들이 단일 그룹만 쓴 것은 "설계 선택"일 수도, "한계 회피"일 수도 있어 **둘 중 무엇인지 소스로 단정 불가**.
  - 확정하려면 `obsidian.md/help/bases/syntax`(또는 설치된 Obsidian의 Bases 버전 릴리스노트)를 직접 확인해야 함 → **검증 필요 항목**.
- **formula/computed property로 계층 키를 합성**(예: 논점번호→대분류 라벨 매핑)할 수 있는지 = 미확인(Bases formula 기능 유무·문법이 소스에 없음).

### 실무적 귀결 (소스로 단정 가능한 부분만)
- 중첩 그룹 지원 여부와 **무관하게**, 현재는 **계층 속성 자체가 frontmatter에 없어** 어떤 그룹화도 1단계(과목)를 넘지 못한다. → "Bases가 못 한다"가 아니라 "**데이터에 계층이 없다**"가 1차 병목. 계층 속성을 넣으면 최소한 **2개 보드(대분류별 1보드씩) 또는 대분류 필터 뷰 다중화**로 계층을 표현할 수 있다(단일 groupBy만으로도). 중첩 groupBy가 되면 1보드로 끝남(미확인이라 옵션 분기).

## 3. 재설계 옵션 비교

세 옵션 공통 전제: 논점노트 695개에 진도속성은 이미 배선됨(미배선 0). 차이는 "무엇을 정본 뷰로 삼고, 계층을 어떻게 복원하느냐".

### (가) 기존 서버보드 유지 + 논점노트 상호연동(sync)만
- **내용**: `board_server`(localhost:8770, 진도_board.html) 정본 유지. Bases는 폐기하거나 읽기전용 보조. 서버 클릭→`진도_state.json`·`learning.json` 갱신은 그대로. 추가로 BOARD 단원키(subj|중분류|단원) ↔ 논점노트(약점/회독)만 단방향 동기.
- **장점**: 이미 3계층(과목>중분류>단원) 보드·약점 빨간테두리·드릴 양방향·시점로그·엑셀내보내기가 완성돼 동작(README L25~58). 계층 그대로. 신규 학습비용 0.
- **단점**: localStorage·localhost 의존(README L18~24) — 휴대폰·다기기에서 안 보임(PKM이 지향하는 "휴대폰 Bases 적극활용"과 배치, PKM구조도 L46). 서버 켜야 자동저장. #49로 은퇴 검토 대상이던 자산을 되살림(핸드오프 L27).
- **사용성**: 데스크톱 단독·단일 사용자엔 최상. 모바일·동기화 시나리오엔 부적합.
- **구현난이도**: 낮음(이미 존재). 동기 다리만 추가.

### (나) Bases를 목차계층 미러링으로 개선
- **내용**: 논점노트 frontmatter에 **계층 속성 추가**(예 `대분류`=민법총칙/채권법/물권담보물권/가족법, 필요시 `중분류`). MOC(`_민법_목차.md`)의 대분류가 1차 출처. 그 위에 .base를 ①중첩 groupBy(지원되면 1보드) 또는 ②대분류별 필터 뷰/보드(미지원이면) 로 재작성. bool/숫자 필터 렌더 검증 동반.
- **장점**: PKM 목표(휴대폰 포함 Bases 네이티브, 서버리스)에 정합(PKM구조도 L46·L53). 목차=고정점 닫힌루프(#50-A)에 가장 부합 — 보드 단위와 쟁점/드릴/약점 단위가 모두 "논점"으로 통일. #49 board_server 은퇴 가능.
- **단점**: (b1) 계층 속성을 695노트에 추가 = 대량 frontmatter 편집(비파괴지만 #45-C 마커·검증 필요). (b2) 중첩 groupBy **미확인** — 미지원이면 보드가 대분류 수만큼 분리(민법 4뷰 등)되어 단일 화면 계층이 안 됨. (b3) 클릭=디스크 자동기록 같은 서버 편의가 사라지고 진도 갱신이 frontmatter 수동/스크립트 편집이 됨(Bases는 표시·질의용, 값 증감 UI 빈약).
- **사용성**: 다기기·검색·필터엔 우수. "한 번 클릭으로 회독+1" 같은 빠른 입력 UX는 서버보드보다 약함(미확인 — Bases 인라인 편집 능력에 의존).
- **구현난이도**: 중~높음(계층 속성 설계·매핑·전수 적용 + 중첩그룹 검증 + 필터 검증).

### (다) 혼합 (서버보드=입력/Bases=열람·계층뷰)
- **내용**: 진도 **입력·집계 정본은 서버보드 유지**(빠른 클릭·드릴 역연동·엑셀), Bases는 **계층 열람·약점/SRS 필터·휴대폰 뷰** 전용. 둘을 논점키·단원키 매핑으로 동기(서버→frontmatter 단방향 미러). 계층 속성은 (나)처럼 추가하되 입력 부담은 서버가 짐.
- **장점**: 양쪽 강점 결합 — 빠른 입력(서버) + 다기기 열람·계층(Bases) + PKM 휴대폰 시나리오 일부 충족. board_server 즉시 은퇴 불필요(점진).
- **단점**: **두 단위 체계(BOARD 단원 202 ↔ 논점 695)의 키 매핑이 핵심 난제** — 1:1이 아니라 1:N(단원 1개에 논점 여러 개)일 수 있어 회독/약점을 어느 쪽 입도로 셀지 정의 필요. 동기 방향·충돌 규칙·중복정의 위험. 유지보수 면적 2배.
- **사용성**: 좋으나 "어디서 입력하고 어디서 보는지" 멘탈모델 학습 필요.
- **구현난이도**: 높음(매핑 테이블 + 동기 스크립트 + 양쪽 정합 검증).

## 4. 추천 (소스 정합 기준)

**1차 추천: (나) Bases 목차계층 미러링**, 단 **계층 속성 추가를 먼저** 하고 중첩 groupBy 지원 여부를 검증한 뒤 보드 형태를 확정.
- 이유: ①핸드오프·#50·#49가 명시적으로 "서버 → Bases 네이티브 대체 + 논점 단위 닫힌루프"를 목표로 정함(핸드오프 L12~13, #50-A). (나)만 이 목표와 정합. ②현 결함의 1차 원인이 "계층 속성 부재"이므로(민법 132 전수 0), 옵션 무관하게 계층 속성 추가는 **선행 필수 작업**이다. ③진도속성은 이미 695 전수 배선돼 추가 비용이 frontmatter 1~2키(대분류) 확장에 그침.

**선행 검증(차단 해소 — #15 블로커 처리)**: (나) 확정 전 반드시 확인할 미확인 2건 —
1. Obsidian Bases가 **다단계 중첩 groupBy**를 지원하는가 (`obsidian.md/help/bases/syntax` 또는 설치된 Bases 버전). 지원=1보드, 미지원=대분류별 뷰 다중화로 설계 분기.
2. `진도보드.base`의 **bool(`==true`)·숫자(`>0`) 필터가 실제 렌더**되는가 (`bases_진행.md` L18 미검증 항목).

**입력 UX가 중요하면 (다) 혼합으로 폴백**: 빠른 클릭 입력을 포기 못 하면 서버를 입력기로 남기고 Bases를 계층 열람뷰로. 단 BOARD 단원(202) ↔ 논점(695) **1:N 매핑 정의**가 선결.

**(가)는 비추천**: 단기 무비용이나 PKM 모바일 목표·#49 은퇴·#50 논점단위 통일에 모두 역행.

> 미확인 표기: 본 절의 "중첩 groupBy 지원 여부"·"Bases 인라인 값 편집 UX"·"formula 합성 가능성"은 워크스페이스 소스로 확인 불가하여 추측하지 않음. 외부 공식문서 확인 후 (나)/(다) 최종 분기.
